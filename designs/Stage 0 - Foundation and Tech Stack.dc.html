Stage 0 — Foundation and Technology Choice

The two weeks of work that make the existing tracker safe to build a CRM on, and the stack the rest of the system should be written in. Every component runs on a permanent free tier — $0 per month, no card required.

Companion to the stage-wise development plan

1. Technology recommendation

Short answer: keep Supabase, replace the front end. The database side of what you built is the right choice and switching it would cost months for no gain. The browser side — one 1,400-line file that rebuilds the page with innerHTML — will not survive nine more stages of features.

Staying at zero, honestly

The free tiers are not trials. Supabase permits commercial use on the free plan and the current allowance is 500 MB of database per project, two active projects, 50,000 monthly active users, 5 GB of egress and 500,000 edge-function calls. For an in-house tool with seven to fifteen users that is not tight. Three constraints do need managing:

  • The 7-day inactivity pause. A free project with no database queries for a week is paused and has to be resumed manually. A tool your team opens daily never trips this; the staging project will, so expect to wake it before use, or point a free uptime pinger at it.
  • No backups on the free plan. There is no daily backup and no point-in-time recovery, so this is the one thing you must build yourself: a GitHub Action running pg_dump nightly into a private repository or Cloudflare R2's free tier. It is half a day of work in Stage 0 and it is not optional.
  • 500 MB fills up at Stage 4. Daily Search Console rows per client are the only thing in this system with real volume. Store daily data for 90 days, roll everything older into monthly aggregates, and keep query-level detail only for tracked keywords. Done that way, fifteen clients stay well inside the cap for years.

Data sources also stay free: the Search Console API, the GA4 Data API and the Meta Graph API cost nothing. Paid rank tracking and backlink authority scores from Stages 4 and 5 are the only genuinely paid items in the whole plan — drop them, use Search Console's own average position for ranking and manual checks for link quality, and the number stays zero. If you ever outgrow the free tier, the escape hatch is an Oracle Cloud always-free VM running self-hosted Supabase, which is still $0 but costs you server maintenance instead.

Keep vanilla JSViable for one more stage, then every new screen gets slower to build. The re-render bug is a symptom of the architecture, not a typo.

Migration approach: no big bang. The current tracker stays live and in daily use. The new app is built beside it against the same database, screen by screen, starting with the Stage 1 account record. When a screen is better in the new app, the old tab is removed. The team never loses a working tool, and no data is migrated because there is only one database.

2. Stage 0 scope

Six workstreams. None of them add a feature; all of them are prerequisites.

0.1 Roles and row-level security · 4 days · highest priority

Today isAdmin() runs in the browser and the anon key is public in the page source. Anyone who signs in with any Google account can query your tables directly with a few lines of JavaScript. The fix is to move the decision into Postgres.

-- 1. role as a real type, on the existing team_members table
create type member_role as enum ('admin', 'manager', 'member', 'client');
alter table team_members alter column role type member_role using role::member_role;

-- 2. helper functions, security definer so policies can call them
create or replace function auth_member_id() returns uuid
  language sql stable security definer as $$
  select id from team_members where lower(email) = lower(auth.jwt() ->> 'email');
$$;

create or replace function is_admin() returns boolean
  language sql stable security definer as $$
  select exists (
    select 1 from team_members
    where lower(email) = lower(auth.jwt() ->> 'email') and role = 'admin');
$$;

-- 3. lock every table, then grant back deliberately
alter table projects        enable row level security;
alter table assignments     enable row level security;
alter table checklist_runs  enable row level security;
alter table offpage_runs    enable row level security;
alter table keywords        enable row level security;
alter table keyword_checks  enable row level security;
alter table team_members    enable row level security;

-- 4. example: members read projects they are assigned to, admins read all
create policy projects_read on projects for select using (
  is_admin() or exists (
    select 1 from assignments a
    where a.project_id = projects.id and a.member_id = auth_member_id())
);
create policy projects_write on projects for all using (is_admin()) with check (is_admin());

Same pattern for every table: read scoped to assignment, write scoped to assignment or admin, team_members writable by admins only. The existing upsert_* RPC functions need the same treatment — check the caller's role inside the function rather than trusting the argument.

Test: sign in with a personal Gmail that is not in team_members, run a select against each table from the browser console, and get zero rows every time.

0.2 Migrations and environments · 2 days

  • Repository created; the current index.html committed as the baseline.
  • Existing schema pulled into versioned migration files with the Supabase CLI. From here no schema change happens in the dashboard.
  • A second Supabase project as staging, seeded with anonymised data.
  • Nightly pg_dump via GitHub Actions into a private repository, verified by actually restoring one dump into staging. The free Supabase plan has no backups of its own.

Test: a schema change can be applied to staging, reviewed, then applied to production by one command.

0.3 Stop the re-render data loss · 2 days

Every loader ends in render(), which replaces the whole main panel. With realtime on and notes saving 650 ms after you stop typing, a colleague's edit can wipe a half-written note and drop the cursor. This is a patch on the legacy app, not a rewrite:

  • Skip the re-render while any input or textarea inside the panel has focus; queue it and apply when focus leaves.
  • Ignore realtime events that originated from this browser session.
  • Preserve scroll position and open sub-tab across renders.

Test: two browsers, same project; type a long note in one while the other ticks checklist items, and lose nothing.

0.4 Error and empty states · 1 day

Every read currently does res.data || [], so a permission failure and an empty table look identical. Surface the error, retry once, and give the "Loading your projects…" gate a real empty state — right now an empty checklist template leaves the app stuck on that message forever.

Test: revoke a policy in staging; the UI says what failed instead of showing a blank board.

0.5 Audit log · 1 day

One table, one trigger, attached to every table that matters. Needed later for client-facing accountability and for answering "who marked this done".

create table audit_log (
  id          bigserial primary key,
  table_name  text not null,
  row_id      text not null,
  action      text not null,          -- insert | update | delete
  actor_email text,
  changed     jsonb,
  at          timestamptz not null default now()
);
create index on audit_log (table_name, row_id, at desc);

Test: change a checklist status and find the before/after in one row of the log.

0.6 App skeleton · 2 days

Not a feature — the runway for Stage 1. Vite + React app created, deployed to Cloudflare Pages behind Google sign-in, connected to the same Supabase project, TypeScript types generated from the schema, Tailwind and the component library installed, and one real screen ported (the projects list) to prove the pattern end to end.

Test: the new app shows the same live project data as the old one, and an unauthorised account sees nothing in either.

4. What I need from you to start

  1. Who is writing the code — you, an in-house developer, or a contractor? The stack recommendation holds either way, but the hand-off detail changes.
  2. Owner access to the Supabase project, and a GitHub organisation to hold the repository.
  3. The current role list: who must be admin, who is manager, who is member.
  4. Confirmation that a two-hour maintenance window is acceptable when RLS goes live, in case a policy is too strict on the first pass.
  5. Whether this stays internal or becomes a product you sell. It does not change Stage 0, but it changes how the account tables are shaped in Stage 1, and that is three weeks away.

5. Definition of done

Stage 0 is complete when an account outside the allowlist can retrieve nothing from any table, two people can work in the same project without losing each other's input, every schema change is a reviewed file in Git, every data change is attributable in the audit log, a verified nightly backup exists off-platform, and a new screen can be added to the new app in hours rather than by editing a 1,400-line file.
